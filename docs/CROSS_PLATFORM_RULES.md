# 跨平台规则规格

状态：已确认（2026-07-29）  
适用范围：Windows C# Core、未来 Apple `AttentionGuardianDomain` Swift Package。  
本文件定义产品行为合同，不定义 Avalonia、SwiftUI、SQLite 表结构、网络同步或视觉样式。

## 1. 目的与实现边界

Windows 保留现有 C# Core；macOS 与 iOS 共享一个新的 Swift Core。两种实现可以使用不同
语言和内部结构，但面对相同输入必须产生相同的业务结果、生命周期变化和可见状态。

- UI 不得自行计算排程、冲突、当前任务或生命周期。
- 持久化层不得用数据库排序或可空字段取代本文件的业务规则。
- 未明确为跨平台合同的 Windows 打包、Apple 签名、系统通知发送、动画与控件交互不在
  本文件范围内。

## 2. 规范数据模型

所有稳定标识使用 UUID；排序稳定的最后比较项为 UUID 的规范字符串升序。时间使用带时区
偏移的确定时刻；日期使用当地日历日期；持续时间精确到整数秒或更高精度，且必须大于零。

### 2.1 当日待办（ScheduledTodo）

字段：`id`、`title`、`start`、`end`、`isMandatory`、`currentSelectionPriority`。

- `end` 必须严格晚于 `start`。
- `scheduleDate` 等于 `start` 在其原始偏移量下的当地日期；事件可以跨午夜。
- `currentSelectionPriority` 是非负整数。新增事件取得当前活动计划中最大值加一；没有
  事件时为零。
- 移动或编辑事件时保留其 `id` 和 `currentSelectionPriority`。
- 名称 `休息` 是模板生成的保留名称：模板插入时初始为普通事件，不能被改名为其他名称；
  插入后允许用户把该事件设为不可移动，也允许再改回普通事件。

### 2.2 未来待办（UnscheduledTodo）

字段：`id`、`title`、`scheduledDate`、`isMandatory`，以及持久化生命周期。

- 它只有日期，绝不参与时间排序、自动顺延、冲突检测或当前任务选择。
- 添加时必须二选一：确定日期，或至少一天后的相对天数；相对天数先以本地“今天”换算为
  确定日期再保存。
- 活动生命周期为 `active`；规划成功后为 `planned`；用户确认删除后为 `deleted`。
  非 `active` 项不得重新出现在活动列表。

### 2.3 当日待办生命周期

持久化生命周期为 `active`、`completed`、`deleted`。

- 当 `end <= now` 时，活动事项转为 `completed`，保存完成时刻，且不再参与任何活动查询、
  排程、冲突、提醒或 UI 列表。
- 用户确认删除的活动事项转为 `deleted`，不得与自然完成混用。
- `completed` 与 `deleted` 都是历史记录；任何整组计划更新都不得物理擦除它们。

## 3. 时间与确定性

### 3.1 区间

所有时间区间为半开区间 `[start, end)`：`start <= instant < end` 时包含该时刻。两个区间仅
在 `a.start < b.end && b.start < a.end` 时重叠；首尾相接不重叠。

### 3.2 本地日期时间

用户输入的当地日期与时间必须解析为确定时刻。夏令时中不存在的当地时间、或出现两次而
无法确定偏移量的当地时间必须被拒绝并要求用户重新选择；不得悄悄猜测一个时刻。

### 3.3 稳定排序

需要排序时依次比较 `start`、`end`、`id`。这个规则适用于计划输出、冲突检测输入和提醒
的“下一事项”选择。

## 4. 当前事项、冲突与首页状态

- 当前事项是所有活动当日待办中包含 `now` 的事项。
- 同时包含 `now` 的多个事项先按 `currentSelectionPriority` 降序，再按稳定排序选择；
  因而最新录入的冲突事项优先成为当前事项。
- 打开应用时才查询 `scheduledDate <= 今天` 的活动未来待办，包含逾期事项；不持续轮询。
- 首页冲突集合只包含 `end > now` 的活动当日待办的不可移动事件冲突。

## 5. 新增当日待办与自动顺延

输入为标题、开始时刻（未指定时取操作当下）、正持续时间和是否不可移动。系统自动计算
结束时刻；UI 不允许用户直接填写结束时刻。

1. 先以现有计划和新事项在内存中完成试算；试算或持久化失败时不得留下部分计划。
2. 新普通事项若碰到一个或多个不可移动事项，整体移动到每个阻挡事项结束后，保持原持续
   时间，直到不再重叠。
3. 新事项之后，只有与已占用区间重叠的普通事项才被连续顺延；一旦后续事项与占用区间
   存在空档，顺延链停止。
4. 被顺延的普通事项同样必须越过所有不可移动事项，持续时间不变；可跨午夜，跨日时
   更新其 `scheduleDate` 并报告跨日结果。
5. 新不可移动事项与既有不可移动事项重叠时，完整计划仍有效并保存；结果必须列出每一对
   不可移动冲突，交给用户在管理页决定顺序。普通事项与不可移动事项的相遇不是冲突提示。

## 6. 管理页重排、编辑、删除与休息

- 普通事项重排后，以原计划最早开始时刻为锚点，按用户要求的顺序连续重算；普通事项遇到
  不可移动事项时整体落在最后一个阻挡事项之后。若实际位置与请求位置不同，返回“回落”。
- 两个或更多重叠或首尾相接的不可移动事项构成连续组。只有组内不可移动事项允许重排；
  从该组最早原始开始时刻起，按组内新顺序连续排布并保留不可移动属性。
- 删除确认前不改变数据。确认删除后，后续事项从被删除事项的原开始时刻向前补位。
- 编辑当日待办允许修改标题、正持续时间、不可移动属性和开始时刻。普通编辑从整条计划最早
  开始时刻重排；修改开始时刻使用下述独立试算规则。
- 若目标新开始时刻落在另一事项的 `[start, end)` 内，先检查该时刻按稳定排序遇到的第一项：
  - 第一项不可移动时拒绝修改，计划保持不变；
  - 第一项为普通事项时，调用方必须提供用户确认的冲突处理模式；
  - `moveExistingAfterEdited`：被修改事项在目标时刻优先开始；第一项保持原持续时间，移动到
    被修改事项结束后；
  - `truncateExistingAtNewStart`：只把第一项的结束时刻截短到目标新开始时刻；其开始时刻不变；
  - 两种模式下，其余后续事项都按确定的新顺序连续重排，并继续遵守不可移动挡板规则。
- 开始时间修改的试算、确认和持久化必须整体成功或整体失败；用户取消确认时不调用应用操作，
  不改变计划。若目标时刻没有其他事项正在执行，则直接以目标时刻放置被修改事项并整体重排。
- 休息模板默认 20 分钟，可改变模板时长并重复插入。每次插入生成新 UUID、标题固定为
  `休息`、初始 `isMandatory = false`；之后可调持续时间、排序、删除或切换不可移动属性，
  但不可改名。
- 未来待办只在用户主动展开后读取；编辑只允许活动项的标题和日期，删除仍需确认。

## 7. 规划转换与原子性

把到期未来待办“规划”为当日待办时，目标当日待办沿用源未来待办的 UUID 和标题。

1. 先把完整试算后的当日计划写入当日数据库。
2. 只有第一步成功后，才把同 UUID 的未来待办标记为 `planned`。
3. 若第二步失败，重试必须检测到同 UUID 的当日待办已存在，只补做 `planned` 标记，绝不
   再插入或再次顺延。

两个数据库不能提供真正的单一事务时，上述顺序和幂等性是必须保留的失败恢复合同。

## 8. 五分钟前交接提醒资格

提醒资格是业务规则；各平台的系统通知发送、权限与去重机制另行实现。

仅在以下全部成立时返回“现在应提醒”：

1. 存在当前事项；
2. 当前事项持续至少五分钟；
3. 存在另一事项，且它的 `start == 当前.end`；
4. 下一事项标题不是 `休息`；
5. `当前.end - 5 分钟 <= now < 当前.end`。

否则返回明确的不符合原因：没有当前事项、当前事项过短、没有首尾相接的下一事项、下一项
是休息，或尚未/已经离开提醒窗口。应用完全退出时不要求后台提醒。

## 9. 跨平台验收合同

实现 Swift Core 前，先建立版本控制的、平台无关的测试向量。每个向量使用固定 UUID、
固定偏移时间、输入操作、期望输出计划、冲突、生命周期变化与布尔标志；不使用“当前时间”
或随机 UUID。C# 与 Swift 测试都必须读取同一批向量。

第一批至少覆盖：

1. `[start, end)` 包含与首尾相接边界；
2. 跨零点当前事项与结束瞬间不再当前；
3. 普通新增顺延、空档停止与持续时间保持；
4. 普通事项连续越过一个和多个不可移动事项；
5. 两个不可移动事项重叠仍保存，并按最新录入优先选择当前事项；
6. 普通顺延进入下一日并更新日期；
7. 普通重排、不可移动挡板回落、连续不可移动组内重排；
8. 删除前补位、编辑后重排、休息模板约束；
9. 到期未来待办、规划幂等重试与确认删除；
10. 自然完成与用户删除分离，历史不被整组更新擦除；
11. 五分钟前提醒的符合与每一种不符合原因；
12. 无效/重复夏令时当地输入被拒绝。

任何规则变更必须先更新本规格和测试向量，再同时更新 C# 与 Swift 测试；任一平台失败都
不得声称行为仍保持一致。
